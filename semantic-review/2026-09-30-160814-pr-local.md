# Per-person WhatsApp chat visibility via `sent_by`

Adds a `whatsapp_messages.sent_by` column recording the user who owns each outbound send, and changes chat visibility so a conversation surfaces for a user either when it is assigned to them (`whatsapp_contacts.assigned_to`) or when they sent at least one message in it. This mirrors the existing email model ("I see what I sent") and lets more than one person operate the same instance while each sees only the threads they actually drove. Panel sends record the logged-in user; sequence/prospection sends record the instance owner (fallback: first active super_admin); inbound and externally-captured messages stay `NULL`.

Watch for: the new per-person filter only runs on the specific-user branch of `getAll`, but that branch is shared by the super_admin's default view — a super_admin landing on the default chat list now also sees every thread where their own id is in `sent_by`, which is a behavior change but not a leak (confirmed). The main risk is that the `EXISTS` subquery relies on the `idx_wm_sent_by` index existing, which is only guaranteed after migration 139 runs against the target DB (confirmed). Test coverage omits the super_admin and `'unassigned'` paths and does not assert the sequence-owner resolution (confirmed).

**Verdict**: APPROVED

## High-level view

The `sent_by` column is populated at every outbound insert: all four panel inserts in `WhatsappController` (text success, text failure, and both media paths) and both sequence-engine inserts, via a new `resolveInstanceOwner()` helper that walks instance owner → first active super_admin → NULL. The webhook insert leaves `sent_by` unset — correct, since a `from_me` echo arriving over the webhook was sent from outside the system. No outbound path was missed.

The visibility change is a single `OR EXISTS` clause added to the specific-user branch of `WhatsappContact::getAll()`, scoped to a single contact via `wm.contact_id = c.id`, so the only widening is the intended one (a sender who is not the assignee).

The migration follows the project's idempotent pattern (information_schema guards for column, index, and FK, matching migration 130) and adds the index the `EXISTS` needs.

The integration test covers the core behavior — sender sees an unassigned thread they sent, a third party does not, assignment still works without `sent_by`, and both axes coexist — and its fixtures pass every `getAll` filter (real phone/JID, `is_group=0`, `is_archived` defaults to 0). It does not cover the super_admin default view, the `'unassigned'` branch, groups, or the sequence-owner resolution path.

### `sent_by` population across every outbound path

The four `WhatsappController` inserts are the text success (`send()`), the text failure record, and the two media inserts (`sendMedia()` and the quick-reply attachment path), each using `$this->currentUser()['id'] ?? null`. The `?? null` falls back to the same "unowned" state as inbound rather than throwing if there is no session.

`WhatsappMessage::create()` passes its `$data` array straight to `Database::insert()` with no column whitelist, so `sent_by` flows through without any model change — worth noting because a whitelisting model would have silently dropped the new key.

Stamping `sent_by` on the webhook insert would falsely attribute an externally-sent message to whoever happened to receive the webhook; leaving it NULL avoids that.

### Sequence-engine owner resolution

`resolveInstanceOwner()` resolves instance owner first (`whatsapp_instances.user_id`), then the first active super_admin, then NULL. Both engine inserts (`doWhatsapp` at ~1273 and `sendWhatsappRaw` at ~2106) use it. The engine has no logged-in user, so attributing the send to the instance owner is what makes the auto-fired thread appear in that person's chat.

The super_admin fallback is not neutral: if an instance has no `user_id`, every automated send routes to whichever super_admin has the lowest id, so that admin's per-person view accumulates all owner-less automated threads. A reasonable last resort, but worth knowing it concentrates visibility on one account.

### The `OR EXISTS` visibility clause

```sql
AND (c.assigned_to = ?
     OR EXISTS (SELECT 1 FROM whatsapp_messages wm
                WHERE wm.contact_id = c.id AND wm.sent_by = ?))
```

Both binds are `$filters['assigned_to']` in sequence, and they are pushed in the same order the placeholders appear, so the parameter list stays aligned — no off-by-one against the other filters appended before and after (instance, service_status, label, search, archived). The subquery is correlated on `wm.contact_id = c.id`, so it can only ever add the contact it is evaluating; there is no path by which one user's send exposes an unrelated thread.

The `'unassigned'` sibling branch (`c.assigned_to IS NULL`) and the `assigned_to_or_unassigned` branch are untouched, so "no owner" and "mine or unclaimed" semantics are unchanged. Groups are unaffected because the controller unsets `assigned_to` before the groups query.

Performance: the `EXISTS` is evaluated per candidate contact row, but `idx_wm_sent_by` (added in 139) lets each evaluation be an index lookup rather than a scan, and the correlation on `contact_id` bounds it. The existing `getAll` query already carries a heavier correlated-subquery load (the last-message join), so this does not change the query's complexity class. It does mean the model now hard-depends on the migration: on a DB where 139 has not run, this clause errors at query time rather than degrading gracefully.

### Super_admin default view

The controller's `contacts()` sets `$filters['assigned_to'] = $user['id']` in the default (no GET param) branch for every role, including super_admin — only the explicit `?assigned_to=all` and `?assigned_to=unassigned` cases diverge. Because the model's specific-user branch now carries the `OR EXISTS`, a super_admin on the default view sees their assigned threads plus every thread they personally sent, where before the default was assigned-only. Not a leak (the admin only gains visibility into threads they themselves sent), but a behavior change on the common landing view that warrants explicit confirmation.

### Migration shape

139 mirrors 130's idempotent structure: information_schema guards for the column, the index, and the FK, each wrapped in `PREPARE/EXECUTE/DEALLOCATE`. `AFTER sent_via` is valid because 130 established that column. The FK's `ON DELETE SET NULL` matches how `whatsapp_instances.user_id` and `whatsapp_contacts.assigned_to` reference `users(id)`, so deleting a user degrades `sent_by` to the same "unowned" state the rest of the schema uses. No backfill, documented as intentional — historical rows stay NULL and remain visible only via `assigned_to`, which is the pre-change behavior for old data.

### Test coverage

The four visibility tests are the right core: sender sees an unassigned thread they sent, a non-participant third party does not, assignment alone still grants visibility, and the two axes coexist on one thread. The persistence test confirms `sent_by` round-trips. Fixtures are self-contained (own users, instance, contacts, messages) and cleaned in `tearDown`, and they clear every `getAll` gate — real phone, `@s.whatsapp.net` JID (not `lead_`/`manual_`), `is_group=0`, and `is_archived` defaulting to 0 — so the rows genuinely reach the filtered branch rather than being dropped earlier.

Not tested: the super_admin default view (the behavior change flagged above), the `'unassigned'` branch, the groups path, and `resolveInstanceOwner()` itself — neither the instance-owner resolution nor the super_admin fallback is exercised, so a regression in the engine's attribution would pass silently. The tests drive the model directly and never exercise the controller's routing of `assigned_to`, so the interaction that actually produces the super_admin behavior change is not covered at any level.
